# SBX-VPN-Client

`sbx` — консольный VPN-клиент для Linux и Windows поверх [sing-box](https://sing-box.sagernet.org).
Без графической оболочки: подписки, выбор сервера, проверка задержек, TUN или прокси,
автозапуск через systemd или Планировщик заданий Windows.

> **Проверено вручную** на Arch Linux (sing-box 1.13, nftables с `policy drop`, WireGuard-сервер
> на той же машине) с реальной подпиской на панели Remnawave: полный TUN-режим, режим прокси,
> маршруты `ru`, переключение серверов на лету, удалённый доступ по WireGuard и LAN при работающем
> туннеле, автозапуск при загрузке. Офлайн-тесты проверяют совместимость Linux-конфига,
> а Windows smoke в CI — разбор подписки, классификацию AxiOm и `sing-box check`.

## Возможности

- **Подписки, а не только серверы.** Формат определяется сам:
  - sing-box JSON (полный конфиг или список outbound'ов);
  - Clash / mihomo YAML (секция `proxies`);
  - base64 или просто список URI: `vless`, `vmess`, `trojan`, `ss`, `hysteria2`/`hy2`, `tuic`, `socks`.
- Из подписки берутся только серверы. DNS, TUN и маршрутизацию sbx собирает сам:
  панели часто отдают конфиг в устаревшем формате, который свежий sing-box не принимает.
- **HWID для панелей вроде Remnawave.** Без него они вместо серверов отдают заглушки.
  Для собственных подписок sbx отправляет `x-hwid` = первые 16 знаков SHA-256 от
  `/etc/machine-id` в Linux или `MachineGuid` в Windows, а также `x-device-os`,
  `x-ver-os` и `x-device-model`. Отключается флагом `--no-hwid`.
- Трафик и срок подписки берутся из заголовка `subscription-userinfo`.
- Группа `auto` (urltest) и ручной выбор сервера. Сервер переключается на лету через
  clash API, без перезапуска.
- **Интерактивное меню** `sbx pick`: стрелки листают, пробел пингует сервер, Enter выбирает.
  Без `curses` или TTY — меню с номерами.
- `sbx test` — задержка до всех серверов. Если VPN не запущен, поднимается временный
  sing-box без TUN.
- Режимы: `tun` (весь трафик системы плюс mixed SOCKS5/HTTP на `127.0.0.1:2080`)
  или `proxy` (только mixed-прокси).
- Маршруты: `ru` (российские домены и IP напрямую, rule-set'ы geoip-ru и
  geosite-category-ru) или `global` (всё через VPN).
- **Раздельная маршрутизация** (`sbx rule via`): домены или готовые списки
  (`geosite:google`, `geoip:telegram`) через конкретный сервер или группу серверов,
  исключения из списков, DNS тем же путём.
- Частные сети (LAN, 10.0.0.0/8, docker) в туннель не идут. Ответы локальных серверов
  по заданным портам (по умолчанию WireGuard `udp:51820` и `tcp:443`) уходят мимо TUN
  через `ip rule` в Linux, чтобы удалённый доступ к машине не отвалился.
- Автозапуск и обновление подписок раз в 6 часов.

## Требования

- **Linux:** systemd, `sudo` и `sing-box` 1.12+ со сборочным тегом `with_gvisor`
  (на Arch — `pacman -S sing-box`).
- **Windows:** для `sbx-windows-amd64.exe` нужен x64; Python не требуется.
  Для установки и управления задачей VPN нужен UAC той же учётной записи.
- **Для скрипта:** Python 3.9+, `PyYAML` только для Clash-подписок.

## Установка

### Linux

```bash
git clone https://github.com/Xenon-Tetraoxide/SBX-VPN-Client
install -Dm755 SBX-VPN-Client/sbx.py ~/.local/bin/sbx
```

### Windows

Скачайте `sbx-windows-amd64.exe` из [Releases](https://github.com/Xenon-Tetraoxide/SBX-VPN-Client/releases),
переименуйте в `sbx.exe` и сохраните в папке из `PATH` или запускайте как `.\sbx.exe` из её каталога:

```powershell
.\sbx.exe core install
.\sbx.exe sub add myvpn 'https://sub.example/xyz'
.\sbx.exe up
```

`core install` скачивает официальный sing-box и проверяет SHA-256. Если ядра нет, sbx
установит его при первом использовании. `SBX_SING_BOX` задаёт путь к своему ядру на обеих ОС.
Можно вместо EXE скачать `sbx.py` и запускать `python sbx.py`.

## Использование

```bash
sbx sub add myvpn 'https://sub.example/xyz'   # добавить подписку и скачать
sbx sub ls                                    # подписки: трафик, срок
sbx update                                    # обновить все подписки
sbx ls                                        # серверы (● выбран, › активный в auto)
sbx test                                      # задержки
sbx pick                                      # меню выбора сервера (или sbx use без аргумента)
sbx use 5 | sbx use германия | sbx use auto   # выбрать сервер без меню
sbx probe [-a]                                # проверка без перехвата трафика
sbx up | down | restart | status | log -f
sbx ip                                        # внешний IP через VPN
sbx enable [--now] | disable                  # автозапуск
sbx mode tun|proxy
sbx route ru|global
sbx rule [proxy|direct|rm ДОМЕН…]             # свои домены: через VPN / напрямую
sbx rule via СЕРВЕР ДОМЕН|geosite:ИМЯ…        # раздельная маршрутизация
sbx add 'vless://…'                           # сервер без подписки
sbx set [ключ [значение]]                     # настройки
sbx set КЛЮЧ --add X | --rm X                 # элемент списка-настройки
sbx --version
```

### Меню выбора сервера: `sbx pick`

| Клавиша | Действие |
|---|---|
| ↑ ↓, PgUp PgDn, Home End | листать |
| пробел | пинг выделенного сервера |
| `a` | пинг всех |
| Enter | выбрать (переключение на лету, без перезапуска) |
| q, Esc | выйти без изменений |

`●` отмечает выбранный сервер, `›` — тот, на котором сейчас стоит `auto`. Задержка подсвечена
цветом: до 150 мс зелёная, до 400 мс жёлтая, дальше или недоступен — красная. Если VPN не запущен,
пинг идёт через временный sing-box без TUN.

### Проверка без риска: `sbx probe`

Поднимает временный sing-box с TUN-интерфейсом `sbx-probe`, но без `auto_route`:
ни маршрутов, ни `ip rule` он не добавляет. Через туннель идёт только тестовый `curl`,
привязанный к интерфейсу. Команда проверяет ядро, серверы подписки, mixed-прокси
и сам TUN, затем всё останавливает. Её можно запускать рядом с другим VPN-клиентом.
В Windows проверяет задержки через временное ядро без TUN.

## Режим AxiOm

Переименуйте тот же файл в `axiom` (Linux) или `axiom.exe` (Windows), запустите скрипт
как `axiom.py` либо установите `SBX_BRAND=axiom`.

- `axiom sub ls` видит профили приложения как `app:ИМЯ`. Активный профиль приложения
  используется для выбора серверов; `axiom sub add ИМЯ URL` создаёт активный профиль,
  а `axiom sub update 'app:ИМЯ'` обновляет подписку. Запросы используют User-Agent
  приложения, без HWID; подписки, созданные в обычном режиме sbx, сохраняют свои заголовки.
- `axiom ls` и `axiom pick`: страна → протокол → транспорт. `axiom use НОМЕР` выбирает
  строку списка, `axiom use 0` — авто. Выбор записывается в настройки приложения. В списке
  авто показывает минимальную валидную задержку; трафик в авто переключает `urltest` ядра.
- Регион читается из приложения: `ru` → российские адреса напрямую, остальные регионы →
  `global`. Регион меняется в приложении, не через `axiom route`.
- Если каталог приложения не обнаружен, режим AxiOm работает с данными sbx. Укажите
  `SBX_AXIOM_HOME` для явного выбора каталога с `db.sqlite` и `configs/`.
  База неизвестной версии, заблокированная или повреждённая открывается только для чтения
  (или не используется): sbx не мигрирует схему, предупреждает и продолжает работать
  с собственными подписками; `down`, `status`, `rule` работают всегда.
- Профили, созданные приложением, sbx не переписывает: при обновлении меняются только трафик
  и срок (если панель прислала `subscription-userinfo`), а свежий список серверов хранится в
  кэше sbx (`subs/axiom-app/<хеш базы>/ID.json`; `last_update` приложения sbx не меняет), пока приложение
  не обновит профиль само. Профили, созданные `axiom import`/`sub add`,
  sbx пишет целиком и оставляет копию `ID.json.sbx-prev`; свои серверы (подписки sbx) остаются
  в списках после серверов приложения, раздел «Свои серверы».
- AxiOm CLI не пересекается с sbx: Linux — `axiom.service`, `axiom-update.{service,timer}`,
  TUN `axiom0` и порты `2180` (mixed) / `9197` (API) (только для нового состояния), настройки `~/.config/axiom/cli`, рабочий каталог
  `~/.local/state/axiom`; Windows — задачи `axiom`, `axiom-update`, `%APPDATA%\AxiOm\cli`,
  `%LOCALAPPDATA%\AxiOm\cli`. `axiom uninstall` трогает только эти имена.
- `--no-elevate` (Windows): вместо запроса UAC сообщить, что не выполнено, и выйти с кодом 2.
  При запросе UAC sbx ждёт повышенный процесс (он работает в своём видимом окне; при ошибке окно ждёт Enter,
  только если вызвавший процесс интерактивен — скрипт получает код выхода сразу)
  и возвращает его код выхода;
  `SBX_HOME`, `SBX_AXIOM_HOME`, `SBX_SING_BOX` передаются ему скрытыми флагами (так же — задаче обновления подписок).
  `sbx` и `axiom` (`up`, `restart`, `connect`) не включаются вместе, если у одной из них TUN или у обеих совпадают
  порты (mixed, API): сначала `down` другой или `--force`. Режим и порты работающей марки берутся из её
  установленного конфига (юнит `ExecStart -c …`, действие задачи Windows); не прочитался — это конфликт.
  Перед изменением общего выбора лучше закрыть окно приложения: оно кэширует настройки.

### Старые команды AxiOm CLI

| Команда | Действие |
|---|---|
| `import URL` / `import файл.json` | Импорт подписки или локального конфига |
| `connect [N]` | Выбрать сервер и включить VPN; `0` — авто, без номера в терминале — меню |
| `disconnect` | Выключить VPN (`down`) |
| `version` | Версия CLI |
| `guide [тема]` | `start`, `commands`, `windows`, `linux`, `tun`, `update`, `troubleshoot` |

Команды принимаются под именами `sbx` и `axiom`. В отличие от старого CLI, `connect`
запускает фоновую службу: для отключения используйте `disconnect`, а не Ctrl+C.

## Самообновление

- `sbx self-update --check` проверяет версию, `sbx self-update` предлагает установку,
  `sbx self-update --yes` устанавливает без вопроса. Текущий файл заменяется после проверки SHA-256.
- `axiom update [--check|--yes]` — то же самое. Подписки обновляет `axiom sub update`;
  `sbx update` сохраняет прежний смысл и обновляет подписки.
- В интерактивном терминале предложение появляется не чаще раза в сутки. Чтобы отключить
  его, задайте `SBX_NO_UPDATE_CHECK=1`. `SBX_RELEASES_URL` переопределяет URL JSON последнего релиза.

### Свои домены: `sbx rule`

```bash
sbx rule                                  # что настроено
sbx rule proxy example.ru                 # всегда через VPN — даже при route ru
sbx rule direct example.com other.org     # всегда напрямую
sbx rule rm example.ru                    # убрать правило
```

Правило действует на сам домен и все поддомены (`*.` писать не нужно), DNS для него идёт
тем же путём. Свои правила проверяются раньше `route ru`; если домен есть в обоих списках,
побеждает `direct` (команда `rule` сама переносит домен из одного списка в другой).
IP-адреса и подсети сюда не подходят — они идут в `exclude` (см. ниже).

Вместо домена можно указать готовый список: `geosite:ИМЯ` (домены, наборы
[sing-geosite](https://github.com/SagerNet/sing-geosite/tree/rule-set)) или `geoip:ИМЯ`
(адреса, [sing-geoip](https://github.com/SagerNet/sing-geoip/tree/rule-set)). sbx скачивает его
при добавлении и обновляет раз в неделю вместе с подписками.

### Раздельная маршрутизация: `sbx rule via`

Отправить часть трафика через другой сервер, а остальное оставить на выбранном:

```bash
sbx rule via 3 geosite:google                       # сервер №3 из sbx ls (или часть имени)
sbx rule via 're:Germany|Германия' geosite:google   # лучший по задержке из подходящих (urltest)
sbx rule proxy geosite:google-gemini                # исключение: Gemini — через основной сервер
sbx rule via direct example.org                     # цель может быть и direct, proxy, auto
sbx rule rm geosite:google                          # убрать
```

Правила проверяются по порядку: `direct` → `proxy` → `via` → `route ru`, первое совпадение
побеждает. Поэтому исключение из большого списка — это тот же элемент в `proxy` или `direct`,
а `google.ru` из `geosite:google` пойдёт по via-правилу, а не напрямую. DNS для via-правила идёт
через тот же сервер, чтобы CDN отдавали адреса рядом с ним. Группа `re:` подчиняется
`auto_exclude`. Если сервера из правила больше нет в подписке, правило временно идёт через `proxy`
(с предупреждением), а не ломает конфиг. Цель и выбранный в группе сервер видны в `sbx rule` и
`sbx status`. Хранится в настройке `via_rules`.

### Настройки (`sbx set`)

Списки можно менять поэлементно, не перечисляя всё заново:

```bash
sbx set exclude --add 203.0.113.7              # IP станет 203.0.113.7/32
sbx set exclude --rm 203.0.113.7 --add 198.51.100.0/24
sbx set exclude default                        # сброс к значению по умолчанию
```

Значения проверяются до записи: домен в `exclude` или адрес в `proxy_domains` — ошибка с
подсказкой. Если sing-box отверг итоговый конфиг, настройка не сохраняется.

| Ключ | По умолчанию | |
|---|---|---|
| `mixed_port` | `2080` | SOCKS5/HTTP на 127.0.0.1 |
| `api_port` | `9097` | clash API на 127.0.0.1 |
| `exclude` | частные сети | что не пускать в TUN (через запятую, `default` — сброс) |
| `bypass_sports` | `udp:51820,tcp:443` | ответы с этих локальных портов идут мимо TUN |
| `bypass_users` | — | весь трафик этих пользователей (имя или uid) идёт мимо TUN |
| `proxy_domains` | — | домены через VPN (удобнее через `sbx rule proxy`) |
| `direct_domains` | — | домены напрямую (удобнее через `sbx rule direct`) |
| `auto_exclude` | — | regex серверов, которые не попадут в `auto` |
| `dns_remote` | `https://1.1.1.1/dns-query` | DNS через VPN |
| `dns_direct` | `77.88.8.8` | DNS для прямых доменов и адресов серверов |
| `ua` | `SFA/1.13 (sbx; sing-box)` | User-Agent: от него зависит формат ответа панели |
| `before_units` | — | юниты, которые стартуют после VPN (например, бот, которому нужен туннель) |

## Где что лежит

- `~/.config/sbx/`: `state.json`, `subs/`, `rulesets/`, `config.json` (права 600, внутри ключи);
- `~/.local/state/sbx/`: рабочий каталог sing-box;
- `/etc/systemd/system/sbx.service`, `sbx-update.{service,timer}`.

В Linux сервис работает от имени пользователя с `CAP_NET_ADMIN`/`CAP_NET_RAW`, а не от root.
В Windows конфиг sbx находится в `%APPDATA%\sbx`, ядро и рабочие данные — в
`%LOCALAPPDATA%\sbx\core` и `%LOCALAPPDATA%\sbx\work`. Задача SYSTEM использует отдельную
копию ядра, конфига и журнала в защищённом каталоге `%ProgramFiles%\SBX VPN\service`.
`sbx log -f` читает журнал задачи. `SBX_HOME` задаёт другой каталог настроек sbx.

### Автозапуск

`sbx enable` включает `sbx.service` и `sbx-update.timer`. Сервис стартует после
`network-online.target`, поэтому должна быть включена служба ожидания сети
(`NetworkManager-wait-online` или `systemd-networkd-wait-online`). Wi-Fi должен подключаться
без входа пользователя: пароль нужно хранить для всех пользователей, а не в связке ключей.
Лимит перезапусков снят (`StartLimitIntervalSec=0`), так что при падениях во время загрузки
systemd не сдаётся.

В Windows `sbx enable` включает запуск задачи `sbx` при загрузке. Задача `sbx-update`
обновляет подписки раз в 6 часов в сеансе пользователя. Из фоновой задачи новые файлы
подписок сохраняются без UAC и попадают в уже работающий VPN (задача SYSTEM) только после
`sbx restart` (UAC).
`bypass_sports`, `bypass_users` и `before_units` в Windows не применяются.

Если VPN уже работает, `sbx install` и `sbx enable` перезапускают его, чтобы движок сразу
работал с новым конфигом: связь прервётся на пару секунд. Остановленный VPN они не запускают.

## Известные особенности

- TUN-стек — **gvisor**. Стек `system`/`mixed` принимает TCP через input-цепочку ядра
  с TUN-интерфейса, и фаервол с `policy drop` на input (nftables/iptables) такие пакеты
  отбрасывает: TCP молча не работает.
- Не запускайте `sbx up` одновременно с другим VPN-клиентом в TUN-режиме: маршруты
  конфликтуют. В Linux `sbx up` проверяет известные клиенты и отказывается стартовать
  без `--force`; в Windows автоматической проверки нет.
- Транспорты xhttp/splithttp/kcp sing-box не поддерживает, такие серверы пропускаются
  с предупреждением.
